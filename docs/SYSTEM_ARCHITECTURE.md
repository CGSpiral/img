# SYSTEM ARCHITECTURE — Project UMBRA

Status: **PROPOSED** (2026-10-27). Not implemented yet. Technical decisions here are logged in
`DECISIONS.md`. Roblox API details are checked against https://create.roblox.com/docs before
implementation, and items marked *(verify)* still need that check.

## 1. Toolchain (proposed, pending DISCOVERY I2)
- **Rojo** maps `src/` to the Roblox DataModel. It supports live sync into Studio and `rojo build`
  to produce a `.rbxl` or `.rbxm` file.
- **StyLua** for formatting and **Selene** (Roblox std) for linting.
- **Lune** (standalone Luau runtime) runs unit tests for pure-logic modules outside Studio.
- **GitHub Actions** CI runs format, lint, unit tests and the definition linter on every push
  (once approved).
- Engine-dependent tests run in Studio through an in-place test runner that the owner triggers.

## 3. Runtime structure
- **Services** (server) and **Controllers** (client) are plain ModuleScripts loaded by one
  bootstrap per side. Each has `Init()` (wire dependencies, no yielding) and `Start()`
  (begin work). Dependencies are explicit `require`s, with no global framework magic.
  No third-party framework dependency is planned (Knit is no longer maintained).
- **Workspace layout:** `Workspace.Map` (static, generated by the map builder),
  `Workspace.Live` (characters and NPCs), `Workspace.Effects` (client-only, per client).

## 4. Combat model (server-authoritative)

### 4.1 Move flow
1. **Input.** InputController turns keyboard/mouse, touch and gamepad input into abstract
   actions (`M1`, `Skill1`…`Skill4`, `Ultimate`, `Block`, `Dash`, `Burst`).
2. **Client prediction.** CombatController checks local state and buffers input for 150 ms
   (provisional). It plays the startup animation and *swing* VFX immediately, for
   responsiveness, then sends `Combat.RequestMove`.
3. **Server validation.** CombatService checks:
   - rate limit
   - the move belongs to the equipped kit
   - the current state allows it (cancel table)
   - cooldown and resource cost
   - the aim direction is a finite unit vector
   - the player is alive and not in a cinematic or safe zone

   Rejected requests trigger `Combat.MoveRejected` so the client can roll back its prediction.
4. **Authoritative timeline.** The server runs the move's frames. At each active window,
   HitboxService queries targets with spatial queries (`GetPartBoundsInBox`/`InRadius`,
   shapecasts for sweeps) against server-side positions. Targets are rewound by the attacker's
   latency, capped at 200 ms, using a 1 s position history per character.
5. **Resolution.** DamageService applies, in order: invulnerability, block or parry, armour,
   damage × combo scaling, hitstun, knockback, then meter gain.
6. **Replication.** The server fires `Combat.HitConfirmed` to clients within relevance range.
   Clients play hit VFX, hitstop, camera shake and sound. *Hit* effects only ever come from
   the server.
7. **Animations.** Animations played by a client on its own character's Animator replicate to
   everyone. The server plays NPC animations.

### 4.2 State machine (server-owned; mirrored to clients via character attributes)
States: `Idle`, `Moving`, `Attacking`, `Blocking`, `Dashing`, `Hitstun`, `Launched`,
`Knockdown`, `Ragdoll`, `Cinematic`, `Dead`. Each move defines which states it can start from
and which moves it can cancel into. Exposed attributes include `State`, `StateEnd`,
`IFrames`, `SuperArmor` and `ComboCount`.

### 4.3 Knockback and stun on player characters
Player characters are physics-owned by their own client. To knock a player back, the server
inserts a `LinearVelocity` on the victim's root attachment. It replicates and the owning
client simulates it. Stun sets movement to zero server-side. AntiExploitService watches
displacement during stun and knockback and flags or corrects violations.
*Known limitation:* an exploiter can locally ignore knockback. This is mitigated by detection
and correction, not prevented outright.

### 4.4 Timing convention
Move definitions author timings in **frames at 60 fps** (startup, active, recovery) for
designer readability. Runtime converts them to seconds and runs on the server clock. Because
network latency is real, parry and dodge windows are designed in milliseconds of tolerance,
not single frames.

### 4.5 Anti-infinite safeguards (values pending approval)
- Per-hit damage scaling decay
- Hitstun decay over a combo
- Juggle limit with rising gravity scaling
- Maximum continuous-stun time, which forces a knockdown with brief invulnerability
- Burst escape on a long cooldown

A Lune "combo search" test brute-forces cancel chains from each character's definitions to
find loops.

## 5. Networking

| Remote | Kind | Direction | Payload (validated) |
|---|---|---|---|
| `Combat.RequestMove` | RemoteEvent | C→S | `moveId: string`, `seq: number`, `aim: Vector3 (unit)` |
| `Combat.RequestBlock` | RemoteEvent | C→S | `active: boolean` |
| `Combat.RequestDash` | RemoteEvent | C→S | `dir: Vector3 (unit, horizontal)` |
| `Combat.MoveRejected` | RemoteEvent | S→C | `seq`, `reason` |
| `Combat.HitConfirmed` | RemoteEvent | S→C | attacker, victim, moveId, hitIndex, position, severity |
| `Fx.Cue` | UnreliableRemoteEvent | S→C | cosmetic cue id + params (drop-tolerant) |
| `Loadout.Select` | RemoteFunction | C→S | `characterId` |
| `Data.Snapshot` | RemoteEvent | S→C | player's own profile view (read-only) |

Rules:
- Every remote is declared once in `Shared/Net/Remotes` together with its payload schema.
  Server handlers never run before the schema check passes.
- Each player has a token-bucket rate limit per remote. Violations are logged, and repeat
  offenders are kicked (thresholds configurable).
- The client never sends hits, damage, positions to teleport to, currency, XP or unlock
  requests that the server would trust.
- No remote accepts an arbitrary Instance to modify. Only IDs that the server resolves.

## 6. Persistence (proposed, pending DISCOVERY I5)
- **ProfileStore** (loleris), after a licence check, provides session locking, autosave and
  `BindToClose` handling. The fallback is a custom wrapper using `UpdateAsync` with
  retry/backoff and session locks.
- The schema is versioned with forward migrations covered by Lune tests.
- If a profile fails to load, the player is kicked with a retry message. They never play on a
  blank profile that could overwrite real data.
- Only ProgressionService awards XP, currency and unlocks, and only from server-observed events.

## 7. Content definitions (data-driven)
- A character module lists its kit (move IDs), base stats, AnimationProfile key, VFXProfile
  key and passive.
- A move module defines: id, displayName, input slot, startup/active/recovery frames,
  hitboxes (shape, size, offset, per active window), damage, hitstun, knockback vector and
  type, block and parry behaviour, cooldown, cost, meter gain, cancel rules, plus animation,
  VFX and sound cue keys.
- Registries map logical keys to asset IDs. A missing or unverified ID resolves to a labelled
  placeholder and is never fabricated.
- The definition linter (Lune) checks every definition against the schema and checks that
  every cue key exists in a registry.

## 8. VFX, audio and camera
- VFXController pools effect templates and scales emission by QualityConfig tier and camera
  distance. It enforces a per-frame budget and cleans up deterministically.
- Effects are spawned client-side from cues. The server never creates particles in Workspace.
- CameraController handles shift-lock, shake (respecting the accessibility scale), hitstop
  (brief local time-freeze of animations) and cinematic ultimate cameras (attacker and
  victim only, pending C4).
- AudioController uses SoundGroups (Master, Music, SFX, UI, Ambience) bound to settings, and
  pools and cleans up 3D sounds.

## 9. Map pipeline
- Layout data (zones, landmarks, spawns, arena bounds) lives in `tools/map/Layout.luau`.
- The builder script runs in Studio edit mode (command bar or a local plugin). It generates
  terrain (`Terrain:FillBlock`/`FillBall`/`FillWedge`…), modular parts and models from a
  kit, and sets Lighting and Atmosphere. The owner then saves the place.
- Map geometry stays in the place file. The builder is idempotent, so it rebuilds `Workspace.Map`
  from scratch. Rojo does not manage `Workspace.Map`, so syncing never wipes hand edits.

## 10. Performance budgets (provisional targets, to be measured in M2/M5)
- 60 FPS on mid-range PC and 30+ FPS on a low-end mobile device.
- Combined active particle cap per client, with tiers in QualityConfig.
- Server Heartbeat work per frame stays under budget with 12 players fighting, measured with
  the MicroProfiler.

## 11. Security checklist (applied every milestone)
Schema validation on every remote · per-remote rate limits · server-side cooldown, range,
target, state and resource checks · no trusted client values · movement sanity checks ·
server-only currency and XP · logs for rejected requests · no `loadstring` · no secrets in
ReplicatedStorage.
